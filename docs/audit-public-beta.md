# Roomie: audit before the public beta

Read-only audit of `main` at `30d2be2` (2026-10-29). Scope: authorization and tenancy, Claim links, the Channel adapters, data and privacy, secrets, input handling and abuse, web security, operations, and whether the copy is honest. Every finding cites `file:line`, and the line numbers are for `30d2be2`. Nothing in the repo was changed except this file. While the audit ran, someone else left uncommitted edits in `src/lib/session.ts`, `src/pipeline.ts` and `src/toolkits/core/dashboard.ts`. They aren't covered here, and `pipeline.ts` line numbers shift by about 5 because of them. One of them is a new Admin hard trigger for 24 h during setup, which adds to B3 and H6.

## Executive summary

The core is in good shape. Every write goes through a service that loads the acting Member from the DB (`services/authz.ts`). Every id lookup is scoped to the session's Group. Claim links are strong and single-use. Operator pages fail closed. Money is exact. Tenancy between Groups held up everywhere I looked.

**It is not ready for a public beta yet.** Four things must be fixed first:

1. **The laptop `.env` points at the only Neon branch, which is production** (and PITR is 1 day). `test:tools`, `evals`, `seed`, `dev-chat`, a local `npm run dev` (scheduler plus the `DEV_AUTH_EMAIL` bypass) and `npm run telegram` (which deletes the prod webhook) all act on real people's data.
2. **Next.js 16.3.8 has critical advisories** (unauthenticated RCE and a Server Actions DoS). A patch upgrade is available.
3. **There is no per-Group or per-person cap on LLM runs.** Anyone can add the public Telegram bot and spam "roomie…" or voice notes. That burns money and the gateway's account-wide rate limit, which takes Roomie down for every Group.
4. **`/privacy` and `/help` promise things the code doesn't do.** Every message goes to Jev and into traces that are never deleted. Every photo and voice note is downloaded or transcribed. Voice notes always get a reply. "Forget me" doesn't make you "Former member". About 2,900 phone numbers of non-users sit in `wa_contacts`.

Right after those come the High items: a kill switch, processing photos and voice only when Roomie is addressed, a WhatsApp group allowlist, complete forget/delete, and confirmation steps for admin tools.

## Per-area notes

### 1. Authorization and tenancy: done well, don't touch
- `lib/session.ts:43-58`: the Member is always derived from the Neon Auth session via `groupsForAccount` and checked against the URL's `groupId`. `ctx.memberId` never comes from the client. Every server action goes through `act()` → `memberSession` (`actions.ts:16-28`). `/api/chat` and `/api/receipts` do the same, and receipts also require `active`.
- `services/authz.ts:58-78`: `requireActive`/`requireAdmin` reload the actor from the DB with a `groupId` predicate, so a forged Ctx can't skip them. Admin-only checks live in the services (settings, Tricks, personality, schedule, simplify debts, members, Splitwise, delete group data, chore and upkeep removal), so hiding controls in the UI isn't the only protection.
- **IDOR:** I checked every id-taking service (Expenses, cart items, checkouts, chores, upkeep, reminders, recipes, members, notes). Each first loads the row with `and(id, groupId = ctx.groupId)`, and member ids in splits, payers, settlements and reminders are checked against the Group's active Members (`money.ts:189-231,523-531`, `reminders.ts:128-134`). I found no cross-Group read or write. Gaps are pending-status reads only (M9) and the upload path (M6).
- Operator gate: `operator-rule.ts:9-15` fails closed, requires a provider-verified email (all 4 auth users are Google and verified; email+password is **off**), and `/admin/*` plus `/api/admin/whatsapp` return 404 (confirmed in prod).

### 2. Claim links and identity
- 32 random bytes (base64url), 24 h, single-use, consumed under `FOR UPDATE` in a transaction. A re-claim by the same Account is a no-op, and "taken" / "already-in-group" are refused (`claims.ts:127-146`). Only the sender can get one, and it goes privately: Telegram's 403 becomes the "press Start" message, so the link never lands in the group (`toolkits/core/dashboard.ts:20-28`). On WhatsApp it goes to the phone JID, or the LID resolved through `recipientOf`. A link is reused while live, not minted in bulk. Weak spots: L4 (plaintext, no unlink).
- Identity comes from the Channel (Telegram `from.id`, WhatsApp `key.participant` / `participantAlt`), so it can't be spoofed in-band. Display names can collide: `memberIdByName` takes the first prefix match (`toolkits/util.ts:15-21`), so prefer ids in confirmations.

### 3. Channel adapters
- **Telegram webhook:** a missing or wrong `X-Telegram-Bot-Api-Secret-Token` is a 401 via `timingSafeEqual`, and so is everything while the secret is unset (`api/telegram/route.ts:12-20`). Fake updates can't be posted. Bots, `sender_chat` and auto-forwards are ignored (`telegram.ts:379`). Strangers' DMs get `NO_GROUP` (fine on Telegram). Only `message` and `my_chat_member` updates are requested.
- **WhatsApp:** `fresh()` drops `fromMe`, stubs, status broadcasts, newsletters, non-user/group JIDs, replays older than 60 s and duplicate ids (`whatsapp.ts:675-686`). Strangers' DMs get one `NO_GROUP` per process. Limits are 0.5 msg/s per chat, 12/min per group and 1/s global. Links go as text, with no previews. Roomie marks messages read but doesn't appear online. The open issues are which groups it joins (H4), what it processes (H2), what it stores (H3) and unsolicited private reminders (M5). The session lives in Postgres (M12).
- Inbound floods: the queue per Chat is unbounded and every message costs a Jev call (B3).

### 4. Data and privacy
- **Logged:** **all** Chat messages (not only addressed ones) go to `chat_messages` before the Gate (`pipeline.ts:111`) and to a trace span (`pipeline.ts:140`). Private DMs and dashboard messages aren't logged to `chat_messages`, but they do enter the Group's memory thread (M3).
- **Mastra memory:** one thread per Group, with `resource = groupId` for working memory and semantic recall (`memory.ts:41-47`). It can't leak across Groups. It never expires. Forget-me deletes `[Name]`-prefixed user messages and the Member's working-memory line (H5).
- **Traces:** `MastraStorageExporter` with `SensitiveDataFilter` (which redacts only key names like token or password) stores full model inputs and outputs: instructions with member facts, 30 lines of chat, tool results. There's no retention (B4). The platform exporter is off on Fly.
- Data inventory is below.

### 5. Secrets and config
- `.env` isn't tracked, `.dockerignore` excludes `.env*`, and there's no `NEXT_PUBLIC_*` anywhere. Client components import only types and pure modules from server code (`admin/whatsapp/panel.tsx:12` is `import type`). `git grep` for keys, tokens, `postgres://user:pass@`, bot tokens and real phone numbers turned up only `.env.example` placeholders and `555` test numbers.
- `DEV_AUTH_EMAIL` is ignored when `NODE_ENV=production` (`dev.ts:4`, `fly.toml [env] NODE_ENV`, `Dockerfile` `ENV NODE_ENV=production`), so it's off on Fly. Locally it's dangerous only because of B1.
- The Docker build placeholders (`Dockerfile:7-10`) are non-secret and only used at build time. `lib/env.ts` lets `.env` override the process env. In the image there's no `.env` (`.dockerignore`), so Fly secrets win.
- Fly secrets (names): COMPOSIO_API_KEY, DATABASE_URL, LLM_MODEL, NEON_AI_GATEWAY_BASE_URL/TOKEN, NEON_AUTH_BASE_URL/COOKIE_SECRET, OPENROUTER_API_KEY, STT_MODEL, TELEGRAM_BOT_TOKEN/USERNAME/WEBHOOK_SECRET, ROOMIE_OPERATOR_EMAILS, WHATSAPP_ENABLED.

### 6. Input handling and abuse
- Money is integer cents end to end. The model passes intent, `toCents` converts and `assertWholeCents` checks (`money.ts:165-168`). Splits sum exactly. All SQL goes through Drizzle. The few `sql\`\`` templates (`members.ts:79-96,164`, `money.ts:415`, `groups.ts:226`) are parameterized, with no string interpolation of input.
- Beta form: zod, honeypot, 3/IP-hash/hour. Votes: coming-soon ids only, 1/Trick/IP/day and 12/hour. Both limits are in memory, so a restart resets them (OK for now).
- Prompt-injection surface: tool-level `requireAdmin` / `requireActive` hold for the *sender* (good). The gaps are confused-deputy (H6) and instruction-only privacy (M4). Outbound text is chunked at 4096 on both Channels. Telegram URL buttons are filtered with `isButtonUrl`.

### 7. Web security
- Server Actions get Next's Origin check. Cookies are `__Secure-` with SameSite=Lax (`lib/auth/server.ts:5-13`). Redirects in `/auth/callback` are relative and normalized (`oauth-return.ts:25-33`, good). Gaps: `/signin` (M1) and missing headers (M2). `robots.txt` disallows `/g/`, `/claim/`, `/auth/`, `/api/` and `/admin/`. `/api/health` exposes only `{ok, app, at}`. `/design` is 404 in prod. Next's production error pages hide stacks, but actions echo messages (L1).

### 8. Operational safety
- One Fly machine (`fly.toml`: `min_machines_running = 1`, auto-stop off), currently 1 machine, version 16, checks passing. `--ha=false` is documented in the `fly.toml` header. The scheduler is guarded with `globalThis`. Scheduled posts and reminders are claimed in the DB (`scheduled_posts` unique, `claimReminder`), so a second process wouldn't double-post. A second *local* process would still send things (B1).
- Backups: Neon PITR is **1 day** (B1). Uploads are lost on every deploy (M6). WhatsApp session loss: a `loggedOut` clears it, and an operator re-links at `/admin/whatsapp`. There's no alert, so watch `fly logs` for `[whatsapp] logged out`.
- What you can see: `/admin/beta`, `/admin/whatsapp`, `fly logs` (`[roomie]` lines), and Studio over the DB, which shows **everything**, including full traces. What you can't: per-Group usage or cost, abuse signals, a list of Groups. Add `/admin/groups` (H1).

### 9. Clean and honest
- The copy-vs-code gaps are B4, H2 and H5, plus "won't show them the group's money" (M9).
- No TODO/FIXME in `src/`. No spike code is tracked (`spikes/` is ignored). The `real-*` screenshots show only seed data (L6).
